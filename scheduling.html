Scheduling a step

Every step answers three questions: prefill or decode, which sequences, and how many tokens of each. Then the CPU has to get out of the GPU's way.

Prefill

How big a bite of the prompt?

A 128K-token prompt can't go through in one step without freezing everyone else, and tiny chunks waste the GPU. The scheduler cuts it.

Chunked prefill

One prompt, several steps

A long prompt is processed in chunks across consecutive steps. While it is mid-prompt, its status stays WAITING; only the step that schedules its last chunk moves it to RUNNING. Some boundaries are forced: a sequence can carry chunk_checkpoints where a chunk must end.

In the release

A token budget per step

The open-source scheduler fills a per-step budget (max_num_batched_tokens, 32,768 in the examples). The chunk is whatever fits in what's left, rounded down to a multiple of the context-parallel alignment so every CP rank gets equal work.

In production

A time budget and a cost model

Tokens aren't equal: a chunk deep into a long prompt attends to more history. Production gives each step a time budget and predicts its time with a fitted quadratic cost(q, c), where q is new tokens and c the prefix already computed. It solves for the largest q that fits, capped at 32,768. Watch the chunk shrink as c grows.

The group agrees

MIN across ranks, and a vote

All data-parallel ranks in an expert-parallel group meet at every MoE layer, so they must take the same kind of step and finish together. The time budget is reduced with an all-reduce MIN; engines that run both phases also vote on prefill versus decode.

Multimodal

Never cut an image in half

An image is one marker token plus N padding tokens. _adjust_chunk_size moves a chunk boundary that lands inside an image either back to the image's start or forward past its last pad, so each image is encoded and attended to in one piece.

Decode

Everyone runs, until memory says no

The batch

Every running sequence takes a step

In a decode step all running sequences go together, up to max_num_seqs. Sequences that just finished prefill (or arrived from a prefill engine) move from the prompted queue into running first.

Room to grow

Each crossing of 128 needs a block

A sequence whose next tokens cross a 128-token boundary needs a fresh block. The scheduler walks the running list and appends slots; if the free list runs dry, it preempts sequences from the other end of the list until the rest fit.

Lengths

One token, or one plus drafts

With speculation on, each sequence's step length is 1 + however many drafts it verifies. The speculative scheduler picks those numbers to maximize expected tokens per second (chapter 09).

decode · one step
Zero-overhead scheduling

The CPU works one step ahead

On by default. The trick is to plan step N+1 before step N has produced its tokens, then fix the plan on the GPU.

The gap

The naive loop idles the GPU

schedule(N) → forward(N) → sample(N) → sync → post-process(N) → schedule(N+1). The CPU needs the sampled tokens before it can plan the next step, so the GPU waits through post-processing and scheduling.

The overlap

Plan while the GPU computes

While the GPU runs forward(N) and sample(N), the CPU runs schedule(N+1), launches forward(N+1), post-processes N−1 and launches sample(N+1). The GPU queue never empties.

The fix-up

Optimistic plans, corrected on the GPU

The CPU plans step N+1 assuming step N's tokens land, advancing each sequence's counters optimistically. On the GPU, small kernels remap the batch, correct each sequence's key length by how many drafts step N actually accepted, and gather step N's sampled tokens as step N+1's inputs. No round trip through the CPU.

CUDA graphs

One launch per decode forward

Decode forwards are captured as CUDA graphs for a ladder of batch sizes: powers of two, then fixed steps. A step pads up to the nearest captured size (padding rows point at slot 0) and replays the graph in a single launch.

"""CPU-side seqlens_q/k lag one step under ZOS: when this
batch overlaps the previous one, fix them on the GPU from
the previous step's sampling results."""
remap_cpu, seqlens_q_cpu, seqlens_k_cpu, has_overlap = prepare_zos_inputs(
    seq_metadata_list, prev.seq_metadata_list, n_seq_with_padding, self.nextn)
if envs.DEEPINFER_ENABLE_MTP_VARLEN:
    compute_seqlens_q_by_confidence_rates(
        total_q, remap[:n_seq], prev.sampler_output.confidence_rates_gpu,
        seqlens_q[:n_seq])
if self.nextn > 0:
    compute_seqlens_k_zos(seqlens_k[:n_seq], seqlens_q[:n_seq], remap[:n_seq],
        prev.sampler_output.num_accepted_tokens_gpu, nextn=self.nextn)

prepare_zos_inputs (C++) works out which sequences in step N+1 were also in step N and builds a remap from new batch slots to old ones.

If speculation lengths are variable, compute_seqlens_q_by_confidence_rates recomputes each sequence's verify length on the GPU from step N's confidence head outputs, which the CPU hasn't seen yet. Then compute_seqlens_k_zos fixes the key lengths from the real number of accepted drafts.

The cost of being one step ahead: a sequence that finished in step N is still in step N+1's plan. Its output is simply discarded. A sequence preempted while its step was in flight is skipped in bookkeeping so it isn't counted twice.

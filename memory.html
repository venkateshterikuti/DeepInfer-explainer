04 Memory

KV memory, one block at a time

Nobody knows how long an answer will be, so KV can't be reserved up front. DeepInfer hands it out in 128-token blocks, and keeps the sliding window in a second, fixed-size allocator of its own.

Paging

Borrowed from operating systems

The idea vLLM introduced in 2023 and that every serious engine now uses: treat KV memory like virtual memory pages.

The problem

Reserving for the worst case wastes most of it

If each request reserves room for its maximum length, most of that room is never written: a request allowed 32K tokens that stops at 2K leaves 94% of its slab empty, and no one else can use it.

Blocks

Fixed-size pages and a table

Memory is cut into equal blocks of 128 token positions. Each sequence keeps a block table: logical block 0, 1, 2… mapped to whatever physical blocks it was given. Attention kernels read through the table, so the blocks never need to be contiguous.

Free list

A doubly linked list of free block ids

The C++ Blocks structure links every free block to the next. Allocating pops from the head; freeing pushes on the tail; each block carries a reference count. Block 0 is never handed out, so 0 in a table means "empty".

Forks

Share full blocks, copy the tail

When a request forks (several samples from one prompt), the child points at the parent's full blocks and bumps their reference counts. Only the partially written last block is copied, so both branches can keep writing. The windowed state slot is cloned too.

Preemption

Out of blocks? Give some back

Decode needs a new block whenever a sequence crosses a 128-token boundary. If none are free, the scheduler preempts a running sequence: frees its blocks, resets its counters and puts it back at the front of the waiting queue to recompute. Structured-output requests are stopped instead, because their grammar state can't be replayed.

GPU memory
The second allocator

One fixed slot per sequence

Sliding-window KV never grows past the window, so it doesn't need pages. It needs exactly one slot per running sequence.

StateBlock

A ring buffer per layer

Each sequence owns one state slot. Inside, every layer keeps a ring buffer of the last 128 window positions plus 6 spare positions that absorb speculative backtracking and copy overshoot. Writes wrap around; the window never grows.

Two regions

What gets saved and what gets dropped

The slot is split in two: a stored region with the window of the first 20 layers, which is worth saving across requests, and a dropped region with the consumer layers' windows and the compression accumulators, which are cheaper to rebuild than to store (chapter 08).

Joint admission

Blocks and a slot, or nothing

A request is admitted only if both the paged blocks and a state slot are available. If the slot can't be had, the scheduler treats it as "try later" even when blocks are free. Slot 0, like block 0, is reserved: CUDA-graph padding rows write there harmlessly.

The free list, in full

csrc/engine/block_manager.hpp · Blockssource
struct Blocks { // GPU block 0 is unused, so 0 means "empty"
    Blocks(int _n) : _blocks(_n), _head(1), _tail(_n - 1), _size(_n - 1) {
        for (int i = 1; i < _n; ++i) {
            _blocks[i].prev = i - 1;
            _blocks[i].next = i + 1;
        }
        _blocks[_n - 1].next = 0;
    }
    int allocate() { int id = _pop_front(); /* ref_count 0 checked */ ... }
    void pin_block(int id);   // ref_count++ (forks, in-flight copies)
    void free(int id);        // ref_count--; back on the list at 0
};

Why a linked list? Allocation and freeing are O(1) and touch only a few integers. With thousands of blocks and hundreds of sequences per step, that matters on a CPU that is already on the critical path.

Why recompute instead of swap? Swapping a preempted request's KV to host memory and back costs PCIe bandwidth and bookkeeping. Preemptions are rare when the scheduler admits carefully, and V4.1's KV is small, so recomputing is simpler. vLLM V1 and SGLang made the same call.

Where is the prefix cache? Not in this release. In production, cross-request reuse goes through a shared storage cluster instead of an in-engine hash table (chapter 07).

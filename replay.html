08 Recomputation

Replay only what you must

When part of a cached prefix is missing, the exact repair can mean thousands of tokens through dozens of layers. DeepInfer replays 128 tokens, accepts a tiny approximation, and nearly halves the cost of prefill.

The problem

Two caches, two lifetimes

Chapter 07's storage keeps long-range block KV for days. The sliding-window state is treated differently, and sometimes it's gone.

Lifetimes

Block KV in storage, window in host memory

Block KV goes to the shared 3FS cluster. The window state is saved only at multiples of 128 tokens, only for the first 20 layers, only in the host memory of the machine that produced it, and nothing is saved partway through a chunked prefill.

The gap

A hit can arrive without its window

A new request may match a long prefix in storage while the window state for the end of that prefix was evicted, never stored, or sits on a machine that's gone. Long-range attention is fine; the last 128 positions' window is missing.

Exact repair

The receptive field grows with depth

To rebuild layer l's window exactly you need layer l's inputs for those positions, which depend on the window of layer l−1 for 128 positions before them, and so on down. Across 20 layers that's 20 × 128 = 2,560 tokens of replay.

Bounded replay

Replay 128 tokens and clip the window

The trick

Start the replay at s, see nothing before s

DeepInfer recomputes only the last 128 tokens of the hit prefix, alongside the uncached suffix, and truncates the window to the replayed segment: the query at position i sees keys from max(s, i−127) to i. Positions near s see a shorter window than they did originally.

What's reused

Block KV untouched; only the window rebuilt

The replayed segment rebuilds the sliding-window KV. Its long-range block KV comes from storage as-is, neither recomputed nor overwritten. The cost is now a constant: 128 tokens, whatever the context length or layer count.

Proof it's the same code path

Mask mode vs compact mode

Truncation can be done by masking rows (simple) or by physically dropping them (fast). examples/yoco/yoco_equiv.py checks they agree: level 1 compares window pivots, visible keys and store slots on one device in seconds; level 2 runs both on 8 GPUs and compares log-probabilities and top-K element by element.

Decoder bounded replay

Half the model skips most of prefill

The same idea applied inside every request, not just on cache hits. It's the single biggest prefill saving in the system.

Recall

Consumer layers don't read the prompt

V4.1's later layers take their long-range KV from the hidden state of the last early layer (chapter 02). So prefill only needs the early layers to run over the whole prompt; the consumer layers' long-range KV falls out of that.

But

Decode still needs their windows

Every consumer layer still attends to its own last-128-token window during decode. Rebuilding those exactly would mean running 2,560 tokens through 20 layers. Instead, prefill runs the consumer layers on just the last 140 tokens: the 128-token window plus slack for speculative backtracking.

Effect

Nearly half of prefill, gone

The replayed windows are used only for decode and never enter the prefix cache. Total prefill compute drops by nearly half. The repo's prefill benchmark is measured with it on: DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact, KEEP_TOKENS=140.

def yoco_enabled(cfg) -> bool:
    """Whether the model enables YOCO
    (layers after n_prefill_layer are consumer layers)."""
    return cfg.get("n_prefill_layer", cfg.num_hidden_layers) < cfg.num_hidden_layers

def is_yoco_consumer_layer(cfg, layer_idx) -> bool:
    """YOCO consumer layer: [n_prefill_layer, n_layer)."""
    return yoco_enabled(cfg) and cfg.n_prefill_layer <= layer_idx < cfg.num_hidden_layers

Settings that must agree. The retained suffix has to cover the window plus the maximum backtracking length, so the defaults are 128 + 6 = 134 for hit capping and 140 kept tokens in decoder replay.

A known cost of preemption. With truncation on, a preempted and recomputed request may produce slightly different results; the engine's step loop says so in a comment.

Why not store everything? The window state for all 40 layers at every 128-token mark would multiply host memory and transfer volume. Storing 20 layers at 128-token marks costs 1.42 MB per sequence, and the rest is cheaper to replay.

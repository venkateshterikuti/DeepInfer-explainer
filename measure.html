Measuring it

A serving engine is only as good as the numbers you can trust about it: how fast it runs, measured so noise can't creep in, and whether it still computes the same thing after every change.

The benchmark

Measure one stage at a time, in steady state

The offline benchmark drives the engine directly, with no server or network in the way, and reports per-GPU speed of prefill and decode separately.

Decoupled stages

One prefix, forked many times

One source request computes the shared cached prefix (by default 28,672 of a 32,768-token context), then forks into many requests that each prefill their own 4,096-token suffix, in chunks of 32,768 tokens per step. Decode then runs 64 of them per rank. Prompts are random non-special tokens, so no special-token path is hit by accident.

Steady state

Skip, log, then measure silently

Prefill skips 5 warmup chunks and measures 10 intervals. Decode skips 50 warmup steps, runs 60 more with periodic logging on (load-balance readings are taken there), then measures 60 intervals with logging off.

Noise

Drop the flush, profile last

Every few steps the MoE load balancer gathers expert statistics across all ranks, which adds about a dozen milliseconds. Intervals containing that flush are dropped. The profiler runs in separate windows at the ends: it inflates step times (by up to half at batch 1), and leaves a 7–11% slowdown after it detaches, so nothing is measured after it.

Accounting

Read the token count carefully

Decode throughput is steps per second × requests × (1 + drafts) ÷ CP: every draft is counted as accepted. That's an upper bound; the real output depends on acceptance. The published curves instead scale by an assumed acceptance, for example 3 drafts at 75% each counted as 1 + 3 × 0.75 = 3.25 tokens per step.

Correctness

Is it still computing the same thing?

Exact baselines

Perplexity, sample by sample

Offline inference records per-sample perplexity for fixed text and image prompts, per platform and per DP rank, and compares it exactly against stored baselines. A long variant uses a 16,389-token input and 4,096 outputs with 5 drafts. A baseline is refreshed only after a numeric change has been confirmed as intended.

Invariance tests

Same answer, different arrangement

Batched versus one-at-a-time must match exactly, for the language model and for the vision encoder. Two logprob passes are compared by KL divergence. The sampler, the EPLB placement policy and nearly every TileLang op have their own tests; the random sampler is checked both statistically and for invariance to row order.

Model quality

End-to-end evals

AIME 2026 (30 problems × 32 samples), HLE (2,500 questions, 342 with images) and GPQA Diamond (198 × 8), all scored as Pass@1. Generation writes raw outputs to disk and scoring runs separately, so the judge can change without regenerating. Prompts are rendered by the encoder shipped with the checkpoint.

Where the decode number comes from

examples/benchmark.py · measure_decodesource
clean = [ts - prev[0] for prev, (ts, flushed)
         in pairwise(stable_decode) if not flushed]
avg_sps = len(clean) / sum(clean)
return {
    "decode_avg_sps": avg_sps,
    "decode_max_step_ms": max(clean) * 1000,
    # full-acceptance accounting: 1 + nextn tokens
    # per request per step; rescale with τ from avg_sps
    "decode_tokens_per_s_per_gpu":
        avg_sps * args.decode_num_requests
        * (envs.DEEPINFER_USE_NEXTN_DECODE + 1) / cp_size,
}

Steps per second is the honest quantity. With fixed-length verification each step always submits 1 + drafts tokens per request, so the step rate doesn't depend on acceptance. Token throughput is a choice of how to count, which is why the raw step rate is saved alongside it.

The slowest step is reported too, and should be close to 1000 ÷ average steps per second. A large gap means something periodic is still inside the window.

Sweeps are one process per point, always with the profiler off, and refuse to plot points whose model, EP size, context or draft count differ.

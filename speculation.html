09 Speculation

Guess, then check

Checking five tokens costs about as much as generating one, so a small drafter guesses ahead and the big model verifies. DeepInfer's DSpark adds a step: it decides, across the whole batch, which guesses are worth checking.

Why it works

Memory-bound steps have room for free tokens

Spare compute

Five tokens for the price of one

A decode step is dominated by reading weights (chapter 01). Running the model over 6 positions instead of 1 reads the same weights, so it costs only a little more. Speculative decoding spends that spare math.

Draft and verify

Guess cheaply, score in one pass

A drafter proposes the next few tokens. The target model runs once over the last real token plus the drafts and produces its own probability at every position. Matching drafts are accepted; the first miss is replaced by a token from the target.

No quality loss

Accept with probability min(1, p ÷ q)

Where the drafter's probability q for its token exceeds the target's p, accept only with probability p ÷ q; on rejection, sample from what's left of p after subtracting q. The output distribution is the target's (up to a tiny numerical guard term). DeepInfer's sampler implements this rule.

The arithmetic

Expected tokens per step

If each draft is accepted with probability α independently, a step with γ drafts yields (1 − αγ+1) ÷ (1 − α) tokens on average. At α = 0.8 and γ = 5 that's about 3.7 tokens per step instead of 1.

The drafter

A block drafter with a sense of order

The code calls it DFlash; the paper calls the system DSpark. Three draft layers with smaller MoEs sit on top of the target model.

Block drafting

Five positions in one pass

Instead of drafting one token at a time, the drafter fills a block of 5 positions in a single forward pass, conditioned on hidden states taken from target layers 37, 38 and 39. The drafter's key cache for real tokens is filled inside the target's forward pass, so the drafter needs no prefill pass of its own.

Markov head

Each guess knows the one before it

Parallel block drafters lose accuracy toward the end of the block, because later positions can't see earlier guesses. DSpark adds a sequential head with a low-rank (rank 256) transition from the previous draft token, recovering much of that decay.

Confidence head

A calibrated guess about the guess

For every draft position, a tiny linear head reads the drafter's hidden state and Markov embedding and outputs, through a sigmoid with a per-position temperature, the chance this draft will be accepted. Multiplying along the block gives each draft's survival probability.

DFlash + Markov + confidence
Confidence-scheduled verification

Check the guesses that pay

The waste

Fixed length verifies hopeless drafts

Verifying all 5 drafts for every request spends compute on positions that will almost surely be rejected, like the fifth draft after a low-confidence fourth. At large batch sizes that compute isn't free anymore.

One queue

Every draft slot in the batch, sorted

The scheduler pools every (request, position) slot in the batch and sorts by survival probability. A request's later drafts always rank behind its earlier ones, because survival only falls along a block.

The objective

Maximize expected tokens per second

Walking down the queue, each extra slot adds its survival probability to expected tokens and one row to the step, which costs time read from a measured step-time curve. The scheduler keeps the prefix with the highest expected tokens ÷ step time, then gives each request 1 + its admitted drafts.

Live calibration

The curve updates itself

The curve starts from profiling. At runtime, a median-of-medians over the last 5,000 steps fits one per-row slope, shared by all graph sizes, for how much slower real steps run than the profiled curve; the sampler's time is a 9-step median. Because of asynchronous scheduling, the total budget uses confidences from two steps back; per-request lengths are finalized on the GPU from last step's.

The scheduler loop

auto update_best = [&]() {
    // smallest captured graph that fits cur_bsz rows
    const auto &[graph_size, baseline_ms] = _decode_perf_curve[cur_bsz_idx];
    const double time_ms = baseline_ms + slope_ms * graph_size + sampler_ms;
    const double cur_throughput = cur_expected / time_ms;
    if (cur_throughput > best_throughput) {
        best_throughput = cur_throughput; best_bsz = cur_bsz;
    }
};
update_best();                         // golden tokens only
for (auto &acc : acc_queue_for_bsz) {   // sorted by survival
    cur_expected += acc.first; cur_bsz += 1; update_best();
}
seqlens_q.assign(num_seqs, 1);
for (int i = 0; i < best_bsz - num_seqs; ++i)
    seqlens_q[acc_queue_for_seqs_q[i].second] += 1;

Graph-aware. Time is read from the captured CUDA graph size that would run, so adding one row that crosses into a bigger graph is charged the jump. The search doesn't stop at the first decline, so it can step past those jumps.

Two queues. One, built from confidences two steps old, sets the total budget; the other, from last step's, decides which requests get the rows.

Grammar-aware. With structured output on, the grammar matcher walks through the drafts to build a mask for each draft position, then rolls all of those steps back; next step it advances by the tokens actually accepted.

Opt-in. Confidence-scheduled verification is off by default; DEEPINFER_ENABLE_MTP_VARLEN=1 turns it on. Otherwise every request verifies all its drafts.

Sampling, structure, determinism

After all the attention and experts, a step ends with one row of 129,280 numbers per request. Turning that row into a token is where grammars, speculative checks and reproducibility all live.

The sampler

From a row of scores to one token

One fused kernel does most of this, on the GPU, for every row in the batch at once.

Logits

Hidden state × embedding table

Only the rows that need a token get scored: the last position of each prompt, or every position of a decode step (the real token plus its drafts). Each row's final hidden state (5,120 numbers) is multiplied by the 129,280-row output embedding, giving one score (logit) per vocabulary entry.

Shortlist

Work on the top few thousand

With DEEPINFER_SAMPLER_FORCE_TOPK set, DeepSelect keeps only the highest-scoring 4,096 (or 1,024) logits per row and remembers their vocabulary ids. Softmax, sampling and verification then run on that short row. Blacklisted tokens are set to −∞ first, and a request can ask that its first token not be end-of-sequence.

Shape

Temperature, top-k, top-p

Dividing by the temperature sharpens or flattens the distribution; top-k and top-p then drop the tail. A log-softmax gives the logprobs that are returned to the caller (up to 1,000 alternatives per position).

Draw

A random number with no state

There is no shared random generator. Each draw hashes the request's 64-bit seed with the token's position (SplitMix64) into a uniform number, then inverts the cumulative distribution. The same request at the same position always gets the same number, whatever else is in the batch.

Verify

Drafts go through the same kernel

For draft rows, the kernel compares the target's probability with the drafter's and applies the accept/resample rule from chapter 09. It also estimates each draft's true acceptance probability, so the engine can track how well calibrated the confidence head is.

Structured output

Only tokens the grammar allows

A JSON schema, regex or EBNF grammar becomes a mask over the vocabulary, recomputed every step on the CPU and applied on the GPU.

Compile

Off the critical path

XGrammar compiles the schema on a worker thread while the engine keeps running other requests. The request joins the scheduler only when its matcher is ready, and is aborted if compiling takes over 20 seconds. Compiled grammars are cached, with a byte limit (10 GiB by default) because an unbounded cache can be grown by distinct schemas until memory runs out.

Mask

One bit per token

Each step, the matcher writes which tokens are legal into a bitmask: 129,280 bits, about 16 KB per row. The CPU fills it while the GPU computes logits; a side stream copies it over, and a TileLang kernel sets every forbidden logit to −∞ before sampling.

With drafts

Masks for every draft position

With speculation, the matcher walks forward through the request's draft tokens, filling a mask for each position, then rolls back the same number of steps. Every verified row gets its own mask in one pass. Next step, the matcher advances by the tokens actually emitted.

Triggers

Free text, then a grammar

A request can pass trigger_token_ids: generation is free until that exact token sequence appears, then the grammar applies, which suits tool calls inside normal text. Partial matches are tracked with a KMP failure table. An optional bound_token_id forces the trigger sequence to follow once it appears.

Determinism

Same input, same output

Two separate guarantees: the model's numbers don't depend on the batch, and the random draws don't either.

The cause

Addition order changes the answer

Floating-point addition isn't associative. Kernels pick how to split and reduce a sum based on the batch shape, so the same request can get slightly different logits depending on who it was batched with, and a near-tie between two tokens can flip.

Batch invariance

Fix the reduction order

DEEPINFER_BATCH_INVARIANT=1 switches DeepGEMM and TileKernels to deterministic algorithms, runs FlashMLA in its batch-invariant mode and avoids one fused prefill path. A test runs 64 prompts batched and one at a time, with 5 drafts, and requires identical tokens and logprobs. NVIDIA only for now.

Deterministic sampling

Seeds, positions, fixed draft length

With batch invariance on and a fixed seq_seed, the hashed draws make sampling repeatable. Confidence-scheduled verification must be off (DEEPINFER_ENABLE_MTP_VARLEN=0), because how many drafts a request gets verified depends on the rest of the batch.

The reference sampler

tilelang_ops/random_sampling.py · random_sampling_refsource
# hash (seq_seeds, 3 * sample_positions + case) to a uniform
# and invert the fp64 CDF
sample_case = 1 if is_nextn_predict else 0
seq = (sample_positions * 3 + sample_case) * i64(0x9E3779B97F4A7C15)
combined = seq_seeds + (seq ^ (seq * (1 << 13)))
u = _hash_to_uniform(combined).unsqueeze(-1)     # SplitMix64
cdf = probs.double().cumsum(dim=-1)
target = u * cdf[:, -1:]
return (cdf > target).long().argmax(dim=-1).int()

This is the pure-PyTorch version that the TileLang kernel is tested against. Because the random number depends only on the seed, the position and which draw it is (fresh sample, accept test or resample after a rejection; the drafter uses an offset seed), reordering the batch can't change any token. The test suite checks exactly that by permuting rows and sampling them one at a time.

Without a seed, each request gets a random 64-bit one, so ordinary sampling stays random across requests.

When a grammar matcher hits an internal error, only that request is killed; raising in the sampling path would stall every rank waiting at the next collective.

One model, many GPUs

V4.1 is too big and too sparse for one GPU. DeepInfer splits attention by request and experts by GPU, then works hard to keep every GPU's share of experts equally busy.

Splitting attention

Split by request, not by matrix

There are three ways to spread attention over GPUs. DeepInfer uses the second everywhere and the third only for very long prompts.

Tensor parallel

Every GPU holds a slice of every matrix

Tensor parallelism cuts each weight matrix across GPUs and all-reduces after each layer. For a model with one shared KV head, it can't split the cache by head, so every GPU stores the whole cache. At TP8 that's eight copies.

Data parallel

Every GPU owns its requests

With data-parallel attention, each GPU runs attention for its own set of requests and stores only their KV. No cache is duplicated and no all-reduce is needed for attention. DeepInfer sets the number of DP ranks equal to the number of expert-parallel ranks.

Context parallel

One giant prompt, several GPUs, equal work

For a single very long prefill, context parallelism splits the sequence across ranks. Causal attention makes later tokens costlier, so a naive split overloads the last rank. DeepInfer's mirror layout gives each rank a chunk from the front and its mirror from the back, then all-gathers the KV.

Expert parallelism

Send tokens to experts, not experts to tokens

Placement

Experts spread across the group

Most weights are expert weights. Spreading them over 64 GPUs leaves each with 7 slots at EP64: (384 experts + 64 spares) ÷ 64. Every decode step, each GPU reads only its own 7 experts' weights.

Dispatch

All-to-all, out

After attention, each token's hidden state is sent to the GPUs that hold its 6 chosen experts. Every GPU sends to every other: an all-to-all exchange over NVLink, run by DeepEP.

Combine

All-to-all, back

Each expert GPU runs its experts on whatever tokens arrived, from every request in the group, and sends results back. The token's home GPU sums the six weighted outputs plus the shared expert's.

Why wide for decode

More tokens per expert, fewer bytes per GPU

Decode is memory-bound: spreading experts thinner means each GPU reads fewer weight bytes per step, and each expert batches tokens from all 64 GPUs' requests. Prefill is compute-bound and long, so it uses the smallest EP that fits and keeps communication low.

Expert load balancing

The slowest GPU sets the pace

Every rank waits at every all-to-all, so one overloaded GPU slows the whole group. Balancing is a statistics problem plus a packing problem.

Skew

Some experts are popular

Routing isn't uniform. Whichever GPU happens to hold the hottest experts receives the most tokens, and the step can't finish until it does.

Statistics

Count tokens per expert, per step

The engine records how many tokens each logical expert received at every step. Decode keeps a 1,000-step window and re-places every 10,000 steps; prefill keeps 100 steps and re-places every 1,000.

Replicate and pack

A greedy placement that respects time

Hot experts get replicas in the spare slots, splitting their load. Then physical experts are placed one by one, heaviest first, on the rank that least increases Σ over steps of the busiest rank's load. Summing per-step peaks, instead of averaging, rewards placements that are balanced at every moment.

Move the weights

Shuffle over NVLink, measure again

Expert weights move between GPUs in the group over NVLink symmetric memory. Measured result: the slowest rank carries 1.090× the mean in decode, and 1.045–1.074× in prefill.

# Objective is independent per layer. For a fixed layer, assign its
# physical experts to ranks so that
#   sum over step i of max over rank j of
#     (sum of loads at step i of experts placed on rank j)
# is as small as possible.
# Greedy: try the current expert on every rank and keep the
# placement that minimizes the objective so far.
for job_index in range(num_physical):
    experts = expert_order[:, job_index]
    vector = vectors[layers, experts]
    torch.add(loads, vector.unsqueeze(1), out=candidates)
    torch.maximum(candidates, peaks.unsqueeze(1), out=candidates)
    torch.sum(candidates, dim=-1, out=scores)

The placement runs for all MoE layers at once as tensor operations, so recomputing it every few thousand steps is cheap. Experts are visited in order of their historical load per replica, heaviest first.

A replica splits its expert's traffic evenly, which is why the loads are divided by logical_count before packing.

The redundant-expert count is a lower bound: the engine rounds num_routed_experts + num_extra_experts up to a multiple of the EP size, separately for the main model and the drafter.

01 First principles

One token at a time

Every answer a language model gives is a loop: run the model, pick one token, append it, run it again. Everything in DeepInfer exists because of what that loop costs.

The loop

A model is a function you call over and over

Scroll through the four ideas that every inference engine is built on.

Step 1 · the function

Tokens in, probabilities out

A prompt is split into tokens. The model reads them and returns one score for every entry in its vocabulary. DeepSeek V4.1 Flash has 129,280 of them, so each call ends in 129,280 numbers.

Step 2 · sampling

Pick one

The sampler turns the scores into probabilities, applies temperature and top-k / top-p filters, and draws one token. That token is the only thing this whole forward pass produced.

Step 3 · the loop

Append it and call again

The new token joins the sequence and the model runs again. A 1,000-token answer is 1,000 trips around this loop. In DeepInfer the loop lives in LLM._run_engine, which calls engine.step() until no request is left.

Step 4 · two phases

Prefill once, decode many times

The first call is different: the whole prompt goes through in one pass. That is prefill, and it is heavy on math. Every later call adds one token. That is decode, it repeats for every output token, and it is where most serving time goes.

The KV cache

Remembering the past costs memory

Attention is what lets a token use its context. Making it cheap is why every engine keeps a cache.

Attention

Each new token looks back

When the model processes the newest token, its query is compared with every earlier token to decide what matters. Every earlier token has to be available.

Keys and values

Every token leaves two vectors per layer

Each token produces a key (what it offers) and a value (what it contributes) in every layer. Those vectors depend only on the token and what came before it, so they never change.

The cache

Compute once, read forever

Recomputing every key and value at every step would make an answer of length n cost on the order of n² token passes. Storing them makes each step compute only the new token and read the rest back. That store is the KV cache.

The constraint

The cache decides the batch

GPU memory holds the model weights and every running request's cache. Free memory divided by KV per request is how many requests can run together. Chapters 04 and 08 are about stretching that number.

The memory wall

Decode waits on memory, not on math

This one fact explains batching, expert parallelism, speculative decoding and most of the rest of the engine.

Bytes

Every step reads the weights

To produce the next token, the GPU streams the weights it needs from HBM into its compute units. On an SM100-class GPU that link moves on the order of 8 TB per second.

FLOPs per byte

One request leaves the GPU idle

Each weight byte fetched for a single token does about 2 floating-point operations. The compute units could do several hundred per byte in the same time, so with one request they mostly wait.

Batching

Share the read

If 64 requests take a step together, each weight byte serves 64 tokens. The step takes about as long, but produces 64 times the output. Batching is the cheapest speedup in inference.

The trade-off

Throughput against speed per user

Bigger batches make each step slower, so each user sees fewer tokens per second. DeepInfer's own benchmark spans about 325 tokens/s per user at 8 requests per GPU to about 26,000 tokens/s per GPU at 256.

Continuous batching

Refill the batch every step

Requests finish at different times. If the batch waits for its slowest member, the freed slots sit empty. Scheduling at every step fixes that, and every modern engine does it.

Where the loop lives

The offline entry point is the LLM class. generate() tokenizes prompts, hands each one to LLMEngine.add_request, then spins _run_engine: call step(), collect outputs, stop when nothing is left.

Each step() is one trip around the loop for every running request at once. It asks the C++ scheduler which sequences run, sends that batch to the GPU workers, samples, and returns finished outputs. Chapter 03 opens that step up.

One detail is already visible here: when no request is unfinished, the loop calls flush_inflight_reqs(). With asynchronous scheduling turned on, the last step's results are still in flight when the loop thinks it is done. Chapter 05 explains why.

deepinfer/entrypoints/llm.py · _run_enginesource
while True:
    unfinished = self.llm_engine.has_unfinished_requests()
    step_outputs = (self.llm_engine.step() if unfinished
                    else self.llm_engine.flush_inflight_reqs())
    for raw_output in step_outputs:
        # outputs are pooled; copy before the next step frees them
        output = RequestOutput.clone(raw_output)
        outputs[output.request_id].append(output)
    if not unfinished:
        break

Other ways to do it

Same loop, different engines

The loop itself is universal. Engines differ in where its bookkeeping runs and how much of it hides behind the GPU.

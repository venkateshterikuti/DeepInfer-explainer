The front door

The engine speaks token IDs. Before a request reaches it, an API call has to become a prompt and the prompt has to become tokens; images have to become hundreds of placeholder tokens. On the way out, a token stream has to become text, reasoning and tool calls again.

Requests in

One conversation, safely encoded

DeepSeek Recipe, released alongside DeepInfer, does the API side. Its behaviour is aligned with DeepSeek's own API.

Three formats

Convert first, render once

Chat Completions, Responses and Messages requests are each converted into one conversation type: messages, images, tools, thinking mode, response format. One template per model version renders that into a prompt, so every API gets identical prompts. If a request sets no max_tokens, the default is 8,192, or 65,536 in thinking mode (131,072 at maximum effort), lowered to whatever context is left.

Special tokens by position

Text can't become a control token

While rendering, Recipe records the exact byte ranges where it inserted control tokens like <｜User｜>. Only those ranges become special token IDs; everything else is encoded as plain text with the special vocabulary removed. A user who types <｜User｜> gets ordinary tokens that spell it, not a new turn.

Parallel segments

Known boundaries, independent pieces

Because the special-token positions are already known, the text between them never needs scanning for special tokens, and BPE never merges across them. Each segment encodes on its own, in parallel, and the results are concatenated in order. Long prompts tokenize faster.

Tokens out

Parsing a stream that arrives in pieces

The engine returns tokens a few at a time. A character, a tag or a tool argument can be split across chunks, so the parser is a state machine that never rescans.

Bytes

Hold half a character

A token can end in the middle of a multi-byte UTF-8 character: a Chinese character is 3 bytes, an emoji 4. Those tokens are buffered until the next ones complete the character, and only then passed to the parser.

Markers

Recognized by token ID

The end of reasoning (</think>) and the start of a tool-call block (｜DSML｜) are found by their special token IDs. If the model writes the same characters with ordinary tokens, they stay literal text and can't end reasoning or trigger a tool call. Text delimiters are matched with incremental KMP, so a marker split across chunks is picked up without rescanning.

Tool arguments

JSON built as it streams

A tool's name is sent as soon as it's parsed. Arguments arrive in DSML parameter tags and are turned straight into JSON fragments: string values escaped piece by piece, arrays and objects passed through as their JSON text. No complete argument object is ever built, so the first fragment of a long argument goes out immediately.

token stream → events
Images

One placeholder, hundreds of tokens

This part is in DeepInfer itself. Each image arrives as one placeholder token and its width and height.

Expand

Rows of image tokens

The engine replaces each placeholder with a start token, then for every row of the image w image tokens and a newline token, then an end token: h × (w + 1) + 2 in all. The vision encoder's 2-D features go into a model whose positions are 1-D, so the newlines mark where rows end.

Geometry

14-pixel patches, merged 3 × 3

The image is resized to a multiple of 14 pixels; the 32-layer vision encoder sees one patch per 14 × 14 square, and patches are merged 3 × 3, so each LLM token covers 42 × 42 pixels. Images under 544 × 544 pixels' worth of area are scaled up; if the tokens would exceed 1,024, the largest size that fits is solved for directly.

Off the main process

Workers, shared memory, cache hits

Forked worker processes decode and resize images and write the tensors into a pinned shared-memory pool; a request becomes schedulable once its images are ready, and stalled workers are detected. If the KV cache already covers an image's whole token span, its bytes are dropped before they're even sent to a worker.

In production

Encoders on their own GPUs

DeepSeek runs vision encoders as a separate stage, one cheaper GPU per instance. A prefill machine picks a vision-encoder machine at random; that machine hands the image to its GPU with the fewest pending patches, counted as (width ÷ 14) × (height ÷ 14). The release has most of the engine side of this; the disaggregated deployment isn't included.

Solving for the largest image that fits

r = height / width                       # (1)
# h * (w + 1) = max_n_token - 2          (2)
max_w_float = math.sqrt((max_n_token - 2) / r + 0.25) - 0.5
max_h_float = max_w_float * r
...
max_w = math.floor(max_w_float)
max_h = math.floor(max_h_float)
beta = min(max_w * patch_size * downsample_ratio / width,
           max_h * patch_size * downsample_ratio / height)
best_width = math.floor(width * beta / patch_size) * patch_size
best_height = math.floor(height * beta / patch_size) * patch_size

Substituting h = r·w into the token count gives a quadratic, r·w² + r·w = N − 2, whose positive root is the line above. No search, no iteration: the widest grid that keeps the aspect ratio and stays under the cap.

Very thin images get special cases so neither side rounds to zero tokens.

The release's LLM.generate takes token IDs or text plus images and returns tokens; the API layer (Recipe) and an HTTP server sit outside it.

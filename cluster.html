The cluster around the engine

In production, engines are parts of a larger machine: separate fleets for images, prefill and decode, a load balancer in front of each, and a 100-PiB cache behind them. The release ships the engine; the deployment Q&A describes the rest.

Disaggregation

Why prefill and decode live apart

Interference

A long prefill stalls every decoder

In a combined engine, a 300 ms prefill step means every user in the decode batch waits 300 ms for their next token. Time-between-tokens spikes whenever someone pastes a long document.

Different shapes

Two jobs, two ideal machines

Prefill is compute-bound: thousands of tokens per step on a few GPUs, smallest EP that fits. Decode is memory-bound: as many GPUs as possible, widest EP. One machine shape can't be optimal for both.

E / P / D

Three fleets

Vision encoders run on single, cheaper GPUs. Prefill runs on ordinary 8-GPU machines at EP2–8. Decode runs on 64–128-GPU supernodes at EP64–128. In practice prefill and decode get roughly equal GPU counts, so the smallest efficient unit is 64 + 64 GPUs.

Hand-off

Ship the KV, not the prompt

After prefill, the request's block KV and its sliding-window KV travel to a decode engine over the same path. V4.1's KV is small enough that prefill and decode could sit in different data centers: about 400 Gbps of interconnect per 8 GPUs. DeepSeek runs them in adjacent ones.

Load balancing

Four balancers, four different problems

Each fleet balances a different cost. None of them routes by prefix, because any machine can read any prefix from storage.

Prefill · tiers

Bucket by length

Requests are sorted by total context into four tiers: under 16K, 16–64K, 64–256K, and 256K and up. Each tier gets its own engines and a per-batch compute cap; the number of engines per tier is reassigned from each tier's share of compute demand in the previous round.

Prefill · pull

Engines pull, ranks share

Engines pull work according to their remaining compute quota. Inside a data-parallel group, each arriving request goes to the rank with the lowest current quota load. No prefix-affinity routing: the cache is shared storage, not local memory.

Decode

Balance batch size and KV length together

Request count sets a GPU's batch size; total KV length sets its attention cost. The decode balancer spreads both at once: short requests go to GPUs with few requests but long caches, long requests to GPUs with short caches.

Vision & experts

Patches and expert loads

Images go to a random encoder machine, then to the GPU there with the fewest pending patches, counted as (width ÷ patch) × (height ÷ patch). Inside each instance, the expert balancer from chapter 06 keeps EP ranks even. Altogether: about 80% of a perfectly balanced offline benchmark.

KV storage

A cache measured in days

Compressed KV turns a multi-turn conversation's history into something worth keeping on SSD for a week.

Three homes

HBM, host memory, SSD

In-flight block KV and state KV live in GPU memory. Sliding-window KV lives in the host memory of the machine that produced it, one copy, found through a directory. Paged block KV lives in a dedicated 3FS storage cluster.

3FS

Erasure-coded, read from any 10 of 11

Data is stored 10+2 erasure coded. A read asks all 11 live nodes of a group and decodes from the first 10 answers. A GC worker per node evicts least-recently-used KV to stay under a disk watermark. TTL: 3 days for agent traffic, 7 for chat, whose long tail of re-reads makes old entries more valuable.

The hit path

Match, fetch, swap in

The Entrypoint matches the request's hash chain against metadata before routing. A separate process fetches hit KV from 3FS into host shared memory. A thread in the engine swaps it into HBM layer by layer during the forward pass, using GPUDirect RDMA: the NIC saturates PCIe without spending GPU cores.

Hit policy

Block KV decides; the window decides the last block

Hit length comes from block KV in 128-token steps, capped at L − 134 (window plus speculative backtracking). If the sliding-window state for the last hit block is missing, the hit backs off one block and that block is replayed (chapter 08).

Operations

Scaling and surviving failures

Autoscaling

Prefill machines scale with the number of non-cached tokens; decode scales with running requests. Changes are rate-limited and bounded, and scale-in is forbidden while quota utilization is above 0.8.

Spare ready machines are kept unassigned in the pool as scale-out inventory.

Draining decode

Wide-EP decode instances are hurt by long-tail requests. A decode engine told to shut down gets a one-minute grace period, then forwards every unfinished request with its KV to other decode engines in one shot.

No request is dropped to scale in.

EP failover

All GPUs in a wide-EP instance form one communication domain, so one bad GPU takes down the instance. On restart the platform sets the EP size to however many healthy GPUs it actually got.

Restarts take minutes; resilience comes from spare quota and request rerouting, not fast restarts.

Storage sizing

Recommended KV storage servers: 20 × 30.73 TB SSDs each, at least 40 GB/s read and 5 GB/s write, sized to hold 24 hours of data. In practice about 14.4 TB of logical KV per online GPU.

Storage nodes fail an order of magnitude less often than compute nodes, so KV survives compute failures.
Other ways to do it

Disaggregation and caching elsewhere

The industry converged on splitting prefill from decode. Where it disagrees is where the cache lives and whether routing follows it.

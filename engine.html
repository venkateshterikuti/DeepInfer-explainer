Anatomy of a step

One call to engine.step() crosses Python, C++ and every GPU in the group. This is the path, part by part, with the files that own each part.

The path of one step

Six stops, three layers

The Python layer orchestrates. The C++ core decides. The workers compute. Scroll to follow a step.

1 · add_request

A prompt becomes a Sequence

LLMEngine.add_request builds a C++ Sequence: token ids, sampling scalars, KV-cache state, speculative-decoding state, structured-output state and a schedule state that starts at WAITING. It joins the scheduler's waiting queue.

2 · schedule()

The C++ scheduler decides

Holding the block-manager lock (and releasing Python's GIL), the scheduler picks a prefill or a decode step, chooses sequences, allocates KV blocks and fills SequenceMetadata objects taken from an object pool. One pybind call, one decision.

3 · broadcast

Every GPU rank gets the same plan

The driver worker publishes the step's inputs through a shared-memory ring buffer (MessageQueue, derived from vLLM) so other worker processes on the node read them without a socket round trip.

4 · execute_model_step

Forward, then catch up, then sample

Each worker runs one fixed round: forward step N, post-process step N−1, sample step N, and, in decode with zero-overhead scheduling on, leave step N's post-processing for next time. The CPU work hides under the next forward.

5 · model runner

Graphs, model, sampler, drafter

Decode steps replay a captured CUDA graph sized to the batch. The main model runs, then the sampler verifies last step's drafts, samples, and runs the DFlash drafter for the next step's proposals.

6 · outputs

Results flow back up

C++ process_outputs appends accepted tokens, checks stop conditions and frees finished sequences. RequestOutput objects come from a pool and are reclaimed on the next step, which is why the Python loop clones what it keeps.

Sequence lifecycle

Every request is a small state machine

A sequence waits, runs, and finishes for one of seven reasons. Preemption sends it back to waiting; chunked prefill keeps it waiting across several steps.

Three engine types

One engine, three jobs

The same code runs as a combined engine, a prefill-only engine, or a decode-only engine. Disaggregated serving (chapter 07) uses the last two.

NORMAL engines vote every few decode steps on whether to prefill. Two kinds of checkpoints exist: at ALL points every data-parallel rank must have prefill work, so one busy rank doesn't drag the others into empty prompt steps; at ANY points a single rank with work triggers prefill, so an isolated rank waits at most that many steps.

PROMPT engines return a (possibly empty) prefill result every step. In production they write KV to storage and pass sequences on.

COMPLETION engines have no prefill path, so they can't recompute a preempted request. The scheduler refuses at startup to run a decode-only engine that would need to.

// NORMAL engine: the whole DP group must take the same kind of step.
// ALL point: prefill only if every rank has prefill work.
// ANY point: prefill if any rank has work (bounded wait for a lone rank).
do_prefill = (_dp_allreduce(want ? 1 : 0, MIN) == 1);  // ALL
do_prefill = (_dp_allreduce(want ? 0 : 1, MIN) == 0);  // ANY
// second vote: did any rank actually schedule a prompt?
// if not, fall back to decode, or "running full + waiting
// non-empty" would loop forever on empty prompt steps.
Why C++

The CPU is on the critical path

At decode speeds a step lasts a few tens of milliseconds, and the CPU must schedule, prepare inputs, and process outputs for hundreds of sequences inside it. vLLM measured that on a small model its GPU was busy only 38% of the time; the rest was API server and scheduler.

DeepInfer moves the per-sequence loops into C++: Sequence, Scheduler, BlockManager, the speculative-length scheduler and the asynchronous input preparation (zos.cpp). Python touches each step a handful of times, not once per sequence. Objects that are created every step, like SequenceMetadata and RequestOutput, come from object pools instead of the allocator.

A DeferredRelease helper in the engine holds onto pooled objects and pinned blocks until the GPU no longer needs them, then returns them in one batch.
